# Decisoes

## Fase 0

- **TypeScript 7.0.2 mantido.** `tsc --noEmit`, tsx, vitest 5 e tsdown funcionam. O TS 7 removeu `baseUrl`, entao o alias `~/*` usa so `paths`. O build nao gera `.d.ts` (e uma API, nao uma lib).
- **tsconfig com `module: esnext` + `moduleResolution: bundler`**, pois o codigo e empacotado pelo tsdown e imports relativos/alias ficam sem extensao.
- **Sem `@fastify/autoload`.** O bundle unico (`src/index.ts` -> `dist/index.js`) nao tem a pasta `modules/` em runtime; os modulos agora sao registrados explicitamente em `buildApp()`. Dependencia removida.
- **tsdown com `fixedExtension: false`** para emitir `dist/index.js` (o padrao seria `.mjs`), mantendo `node dist/index.js`.
- **pnpm 12.18.0** fixado em `packageManager` (sem hash). pnpm 12 bloqueia scripts de build: `pnpm-workspace.yaml` usa `allowBuilds: { esbuild: true }` (o antigo `onlyBuiltDependencies` nao e mais respeitado). O tsdown pede aprovacao de "agent skills" no install; nao e necessario.
- **`env.ts`**: validado no import (falha com mensagem clara e `process.exit(1)`), agrupado em `http`, `auth`, `db`. `REDIS_URL` virou opcional (so o `Cache` legado usa; sai na Fase 3). `SESSION_SECRET` exige 32+ caracteres (exigencia do `@fastify/session`). Nos testes as variaveis vem de `vitest.config.ts`.
- **`jsonwebtoken` e CJS**: importado pelo default export, pois o bundle ESM nao resolve named exports.
- `.tool-versions`: `nodejs 24.21.0` (asdf nao resolve `24` sem patch).

## Fase 1

- **Versoes**: fastify 5.12.8, @fastify/cookie 11, cors 11, session 11, swagger 9.9.3, @scalar/fastify-api-reference 1.77, fastify-plugin 6, zod 4.6.7, fastify-type-provider-zod 7.0.0. Zod 4: `z.email()` / `z.url()` no lugar de `z.string().email()/url()`.
- **Formato unico de erro** `{ error, message, statusCode, issues? }` via um unico `setErrorHandler` + `setNotFoundHandler` (`src/utils/error-handler.ts`, que substitui `parse-zod-error.ts`). `error` e o nome HTTP do status; `issues` (`{ path, message }`) so em 400 de validacao, com `path` tipo `body.email`. No type provider 7 o `path` do issue Zod nao vem em `params`; usa-se `instancePath`.
- **500**: sempre logado com o logger do Fastify; em `production` a mensagem e generica (sem stack/mensagem interna). Erros 4xx lancados por handlers mantem status e mensagem. Erro de serializacao de resposta tambem vira 500.
- **`generate-schema-handler.ts`** virou `routeSchema({ response, status, protected, ... })`: monta o `response` map com 400/500 (e 401 se `protected`) usando o mesmo `errorResponseSchema`. Sem tags especificas do projeto; titulo do OpenAPI vem do `package.json`.
- **Docs**: Scalar em `/docs/` (`/docs` redireciona 301), spec em `/docs/openapi.json` (OpenAPI 3.0.3, default do swagger).
- **Testes de erro** usam uma app Fastify minima (`registerErrorHandlers`) com rotas de teste registradas dentro do teste, sem rota falsa no codigo de producao. O modo producao e simulado com `vi.spyOn(env, 'nodeEnv', 'get')`.
- Middlewares legados (`verify-auth`, `verify-token`, `registry-session`) ajustados para o mesmo formato; saem na Fase 3.

## Fase 2

- **Versoes**: drizzle-orm 0.45.4, drizzle-kit 0.31.11, postgres 4.1.0, mongoose 9.12.0. `@paralleldrive/cuid2` removido (ids agora sao uuid no Postgres e ObjectId no Mongo).
- **Mongoose em vez do driver `mongodb` (muda a P4)**: decisao do dono, por maturidade e familiaridade (Papr descartado). `schema.mongo.ts` guarda o `Schema` (campos, validacao, indices, `timestamps`) e o model; o validador `$jsonSchema` foi dispensado (a validacao do Mongoose o substitui). O adaptador usa o model com `.lean()` e mapeia para o tipo de dominio (`id` string vindo de `_id`); nenhum documento ou `ObjectId` sai do adaptador. A dependencia `mongodb` nao e importada diretamente e foi removida.
- **Conexao dedicada** (`mongoose.createConnection`, nao o `mongoose.connect` global), com `autoIndex`/`autoCreate` desligados: `connect()` cria as colecoes e roda `syncIndexes()` no boot (idempotente; `syncIndexes` tambem remove indices tirados do schema). `pnpm db:indexes` faz o mesmo isoladamente. Os models sao criados sob demanda na conexao (`userModel(conn)`, `todoModel(conn)`), agregados em `src/infra/db/mongo/models.ts`.
- **Estrutura**: `src/infra/db/{postgres,mongo}/` com `env.ts` (variaveis do proprio banco: `DATABASE_URL`; `MONGODB_URI`, `MONGODB_DB`), `connect.ts` e `index.ts` (`connect`, `loadEnv`). `src/infra/db/index.ts` e o unico ponto de escolha (re-export de `./postgres`). Ninguem mais importa `infra/db/postgres|mongo` alem dos adaptadores `*.postgres.ts`/`*.mongo.ts` e dos testes (`src/test/db.*.ts` incluidos). `src/env.ts` nao tem mais variaveis de banco; `loadEnv()` do banco e chamado em `index.ts` (falha com mensagem clara listando todas as variaveis invalidas).
- **Postgres**: agregador de tabelas `src/infra/db/postgres/schema.ts` (importa os `schema.postgres.ts` dos modulos); `drizzle.config.ts` e `migrations/` ficam em `src/infra/db/postgres/`. Migracoes regeneradas do zero (as antigas foram descartadas). `pnpm db:migrate` roda o migrator do drizzle (`migrate.ts`, via tsx e `.env`) em vez do `drizzle-kit migrate`, para o mesmo codigo servir aos testes. Ids `uuid` com `defaultRandom()`.
- **Modulos**: `routes.ts` (HTTP fino; recebe o repositorio como opcao do plugin) -> `service.ts` (retorna `Result`, `src/utils/result.ts`; erros `not_found`/`conflict` viram 404/409 via `toHttpError` e passam pelo handler unico) -> `repository.ts` (interface + tipos de dominio). IDs malformados nos adaptadores retornam `null`/`false` (404), nunca erro de banco.
- **`users`**: comportamento mantido (POST emite sessao legada; corrigido na Fase 3). `picture` agora e `string | null` no GET. **`todo`**: CRUD completo (`GET/POST /todos`, `GET/PATCH/DELETE /todos/:id`), **sem `userId` por enquanto**: ownership depende de auth (Fase 3).
- **Raiz de composicao**: `buildApp({ repositories })` passa cada repositorio como opcao do plugin de rotas (sem decorate; tipado e explicito). `src/index.ts` faz `connect(loadEnv())`, injeta e fecha o banco no shutdown. Testes HTTP sem banco usam `noRepositories` (`src/test/no-repositories.ts`): proxies que falham alto se algum repositorio for usado. Nao ha adaptador em memoria.
- **Testes (P5/P11)**: uma suite de contrato por repositorio (`repository.contract.ts`) e uma suite de rotas do todo (`routes.contract.ts`, via `app.inject`), executadas por `*.postgres.test.ts` e `*.mongo.test.ts` contra bancos reais. Vitest com 3 projetos selecionados pelo nome do arquivo: `unit` (tudo menos os de banco), `postgres`, `mongo`; os de banco rodam sem paralelismo entre arquivos (compartilham o banco) e sempre usam bancos `app_test` (a config sobrescreve `DATABASE_URL`/`MONGODB_*` por `TEST_DATABASE_URL`/`TEST_MONGODB_URI` ou pelos padroes do compose; nunca o banco de dev). O global setup do Postgres cria `app_test` se faltar e aplica as migracoes.
- **Scripts**: `test` = so unit (sem banco, rapido); `test:postgres`, `test:mongo`, `test:all`; **`check` = lint + typecheck + `test:all`** (exige os dois bancos no ar: `pnpm db:up:postgres && pnpm db:up:mongo`); **`check:fast`** = lint + typecheck + `test` (sem bancos). Tambem `db:up:postgres|mongo`, `db:down`, `db:generate`, `db:migrate`, `db:studio` (Postgres), `db:indexes` (Mongo).
- **Compose**: profiles `postgres` (postgres:18-alpine, host 5433 para nao colidir com um Postgres local), `mongo` (mongo:8, replica set `rs0` de 1 no; mongod escuta na 27018 dentro e fora do container e o `rs.initiate` anuncia `localhost:27018`, entao `?replicaSet=rs0` funciona do host; o healthcheck inicia o replica set) e `redis` (mantido a pedido do dono; o codigo de cache e sua reorganizacao ficam para a Fase 3). `up --wait` usa os healthchecks.
- **Ambiente desta maquina**: o Docker nao cria redes bridge aqui (modulo `veth` ausente no kernel em uso); a verificacao usou um override `network_mode: host` fora do repositorio. O compose do template usa o modo bridge padrao.
- **Para a checklist "Escolhendo o banco" (Fase 5)**: pastas `src/infra/db/<outro>/`, `**/*.<outro>.ts`, `**/*.<outro>.test.ts`, `src/test/db.<outro>.ts`, `src/test/global-setup.postgres.ts` (Postgres), projeto de teste no `vitest.config.ts` e as variaveis `process.env` de teste, deps (`drizzle-orm`, `drizzle-kit`, `postgres` | `mongoose`), servico do compose, scripts `db:*`/`test:*`, variaveis do `.env.example`, linha em `src/infra/db/index.ts`.
